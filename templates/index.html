• Multiple applicants request the same available room/bed.
How can duplicate allocation be prevented?

When multiple students submit simultaneous requests for the exact same bed at the exact same millisecond, a race condition occurs. To prevent duplicate allocation, the system protects the critical section (availability check → reserve → record) using a Threading Mutex (threading.Lock()). Access is strictly serialized: the first thread reserves the bed, and all subsequent concurrent applicants immediately detect that the bed is occupied, guaranteeing 100% duplicate prevention.

❓ University OS Lab Concurrency Guide
Problem Statement: Multiple students race to allocate the same available bed simultaneously. Without synchronization, two students get booked into the exact same bed (double allocation).
🔒 Single-Bed Contention (Mutex Lock):

For 1 specific bed, a binary threading.Lock() wraps the Critical Section (Check Availability → Reserve Bed → Commit Occupant Record). Exactly 1 thread enters, all competitors are blocked.

🚦 Multi-Bed Capacity (Counting Semaphore):

For > 2 beds (e.g. 100 beds vs 150 applicants), a threading.Semaphore(100) manages finite permits. Exactly 100 applicants acquire permits for 100 unique beds; the 50 overflow requests are safely blocked when count hits 0.
